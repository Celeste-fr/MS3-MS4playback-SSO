# Playability checker, built in

Branch `playability-checker` (started 2026-09-27). The owner: "deprecate this plugin and fully
integrate it into the 3.7 fork". The plugin (`~/MuseScore/orchestration-checker`, MuseScore 3.6
QML, sourcebook of textbook references in `data/tables.py`) is frozen from now on; this is its
successor. Its rules, limits and references carry over unchanged unless noted; the plugin's
headless test scores and their checked results are the parity tests.

## What changes by being built in

- **Nothing is written to the score.** The plugin coloured noteheads (or drew symbols over them)
  outside the undo stack; here the colours are decided when a note is drawn (`Note::draw`, like
  MuseScore's own out-of-range colours), from results kept beside the score. Files stay exactly as
  MuseScore 3.6 reads and writes them (the fork's round-trip rule), and printing / PDF export show
  no marks.
- **No copy reader.** Slurs, staccato dots, hairpins, tremolos and harmonic circles are read from the
  score directly (the plugin wrote a copy of the file to find them).
- **Microtones** come from `ScoreTuning` directly (the plugin read `Note.microtonalTuning`).
- **Open strings**: their mark can be switched off, and its look is the owner's choice (page
  "Open String Colour", https://claude.ai/artifact/YYwpUqGSMdLLvByhShbEbj: colours, or a small 0 /
  a ring instead of a colour, which only a built-in checker can draw).
- Speed: a whole-score pass in C++ is expected in milliseconds, so the checker re-runs after each
  edit (debounced) without the plugin's ranged passes and caches.

## Parts

| Part | Where | From the plugin |
|---|---|---|
| Rules and limits (strings: tuning, reach, bow seconds, jeté, staccato groups, fast runs, tremolo; section vs single player) | `libmscore/playabilityrules.{h,cpp}` | `strings/strings.js` |
| Harmonics (natural, artificial) | `libmscore/playabilityrules.cpp` | `strings/harmonics.js` |
| The pass: walks the score, per note a mark, per problem a row | `libmscore/playability.{h,cpp}` | `core/analyse.js` |
| Wind register data (T1 ranges, T2 registers, T19 dynamic curves, sounding pitch) | `libmscore/playabilitywinds.h`, generated by `tools/playability/gen_winds.py` from the sourcebook | `winds/winds.js`, `data/export_winds.py` |
| Drawing the marks | `Note::draw` | overlays / `note.color` |
| Panel: table (mark, Bar, Staff, Reason), row ↔ selection, Selected line | `mscore/playabilitypanel.{h,cpp}` (dock) | `orchestration-checker-live.qml` |
| Diagrams: fingerboard (stops, natural harmonics), wind register graph | `mscore/playabilitydiagrams.{h,cpp}` (QPainter) | `strings/fingerboard.js`, `winds/registergraph.js` |
| Preferences: checker on/off, open-string marks on/off and style | `mscore/preferences`, *View* menu | — |
| Tests | `mtest/libmscore/playability` (`tst_playability`) | `proto/*-tests.mscx`, the plugin's results |

## Order of work

1. Rules and the pass for stops, open strings, microtones, harmonics, div./unis.; marks drawn;
   preferences; `tst_playability` against the plugin's results on its test scores.
2. Bowing: slur timing (S11), jeté and slurred staccato (S10), fast bass runs (S12), fingered
   tremolo (S13), section vs single player.
3. The panel: table, sorting (bar, then staff), marks column, row → blue range box, score → row,
   Selected line with spelling and microtones.
4. Diagrams: fingerboard and harmonic board, wind register graph with its chips.
5. A Windows build for the owner; the plugin's README says where it went.
